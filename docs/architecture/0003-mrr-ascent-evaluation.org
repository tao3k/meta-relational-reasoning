#+title: RFC 0003 - Bounded MRR Ascent Evaluation
#+status: accepted

* Context

The MRR core owns identities, relation schemas, facts, queries, rules, transitions,
lineage, and bundle validation.  =mrr-ascent= is a downstream execution adapter.  It
must not invent identifiers, publish facts, admit lineage, reinterpret transitions,
or become a second semantic authority.

* Ownership

flowchart LR
  B[mrr-bundle<br/>validated relations/facts/rules] --> A[mrr-ascent<br/>bounded evaluation]
  I[mrr-identity<br/>caller-owned IDs] --> B
  A --> C[ClosureReceipt<br/>pack + generation + inputs + digest]
  C --> L[mrr-lineage admission<br/>validates caller-assigned IDs]
  T[mrr-transition] -. materialize generation first .-> B
  A -. never publishes .-> X[(live relation state)]
#+end_src

The adapter currently owns one deliberately narrow program shape:

1. =reachable(x,y) :- edge(x,y)=;
2. =reachable(x,z) :- reachable(x,y), edge(y,z)=.

Both relation and rule identities come from the validated bundle.  The two rules
must belong to the explicitly selected =RulePackId=; a rule found only in another
pack fails closed.  Variable names are irrelevant; equality and join positions
define the accepted shape.  Other programs fail closed instead of being silently
approximated.

** Search-factor Ascent adapter

=mrr-search= owns a second, equally narrow Ascent program for the POO Search
framework.  It does not extend =mrr-ascent='s validated ReasoningBundle rule
shape and does not pretend consumer factors are MRR bundle rules.  Its only
relations are declared factor edges, generation-bound factor observations,
shortest factor reachability, and candidate influence.  POO Flow owns temporal
causal traces; =mrr-lineage= owns the resulting explanation graph and Impact.

This vertical adapter is separate so text retrieval, scoring, tokenization,
parser facts, and consumer-specific operators cannot leak into the general MRR
closure engine.  Both adapters use Ascent as a maintained fixed-point substrate,
apply finite pre-execution budgets, reconstruct deterministic witnesses, and
return inert receipts rather than publishing state.

* Why Ascent

MRR needs a maintained fixed-point implementation, not another hand-written
closure engine.  Ascent is embedded in Rust, accepts ordinary typed Rust values,
and expresses Datalog-style forward inference without adding a service, a second
runtime, or an FFI boundary to the public facade.  That makes it suitable for the
narrow execution responsibility above while the MRR crates retain ownership of
identity, evidence, lineage, transitions, and publication.

This is a boundary decision, not a claim that Ascent is the semantic model or
that it is universally faster than every alternative.  The
[[https://s-arash.github.io/ascent/cc22main-p95-seamless-deductive-inference-via-macros.pdf][Ascent paper]]
describes the macro-based integration of deductive inference with Rust.  MRR
uses that maintained evaluation substrate and independently checks its output;
the =ClosureReceipt=, deterministic witness reconstruction, admission rules, and
public identities remain MRR contracts.

The evaluated alternatives are:

- a hand-written graph or closure loop would duplicate fixed-point, join, and
  indexing machinery and would couple one current rule shape to the engine;
- [[https://github.com/souffle-lang/souffle][Souffle]] is a strong compiled Datalog
  implementation and research reference, but its generated C++ pipeline would
  add a separate build and language boundary to this Rust facade;
- direct graph traversal is appropriate for isolated graph algorithms, but is
  not the intended abstraction for typed relations and multiple rule packs.

The choice must be revisited if Ascent cannot preserve deterministic bounded
receipts, cannot meet the measured scale envelope, or prevents a required
deployment target.  Such a replacement may change the proposal engine; it must
not weaken or bypass admission.

** BYODS as a representation optimization seam

[[https://doi.org/10.1145/3622840][Bring Your Own Data Structures to Datalog
(BYODS)]] shows that a Datalog program can retain declarative rule semantics
while compiled joins operate over a user-provided relation representation.  It
targets cases where generic B-trees or hash maps impose algorithmic overhead
that a domain structure such as union-find or a lattice can avoid.  The work is
in the same Rust-embedded Datalog research line as Ascent and is relevant to
large Content Graph closures.

MRR does not currently implement BYODS.  If profiling identifies
representation-imposed cost, a future evaluator may adopt a specialized
relation only after an A/B scenario proves semantic parity, deterministic
receipt parity, and material scale improvement.  The optimization may change
candidate computation; it may not change source identities, rule meaning,
generation binding, witness requirements, or the all-or-nothing admission
boundary.

* Bounds and deterministic evidence

= Bounded closure contract

Let $V$ be the distinct string-valued endpoints in the admitted source facts and
$E subset.eq V times V$ the source relation.  Before Ascent runs, the adapter
checks

$ abs(E) <= L_("input") quad and quad abs(V)^2 <= L_("pairs"). $

The second inequality is an allocation-safe upper bound on the finite binary
closure domain.  Ascent computes the least fixed point

$ R_0 = E, quad R_(n+1) = R_n union (R_n compose E), quad
  R^* = union_(n >= 0) R_n. $

For every $(x,z) in R^*$ the receipt carries a shortest support sequence.  Equal
length witnesses are ordered lexicographically by caller-owned =FactId=.  The
receipt also binds the selected rule pack, input generation, complete sorted input
=FactId= set, status, and sorted candidates under the
=mrr.derivation-receipt.v1= SHA-256 frame.  Repeated evaluation of the same bundle
and generation therefore yields the same candidate evidence and digest.

The output limit changes only receipt cardinality.  It never changes the computed
fixed point, and truncation is explicit as =ClosureStatus::OutputTruncated=.
#+end_src

* Failure and admission boundary

Bundle validation, missing or non-binary schemas, rule-shape mismatch, non-string
source facts, source facts from another requested generation, seeded facts in
the derived relation, input capacity, and pair capacity are checked before
evaluation.  Seeded derived facts fail closed until this adapter evaluates
their recursive consequences rather than silently omitting them.
Bundles containing transitions are rejected until an upstream owner materializes an
exact semantic generation.  Evaluation returns =DerivationCandidate= values containing the
derived relation, values, rule, generation, and ordered supporting =FactId=s.  A later
=mrr-lineage= admission owner remains responsible for allocating =DerivationId= and
committing lineage.  Cancellation or failure therefore cannot partially mutate live
relation state.
* Atomic closure admission at the facade boundary

=mrr-ascent= ends at a deterministic =ClosureReceipt= containing ordered
=DerivationCandidate= values but no allocated output identities.
The =meta-relational-reasoning= facade composes that receipt with identities
allocated by its caller, while the existing owners retain their authority:
=mrr-lineage= validates every derivation and =mrr-transition= validates the
whole immutable semantic-generation delta.  The facade returns =MaterializedClosure= only
after all validations succeed; it owns no live publication or partial commit.
The facade also requires the existing =SemanticSnapshot= at evaluation,
physical-pair comparison, and materialization.  Its in-process
=BundleBoundClosure= retains the source bundle identity and snapshot digest;
both boundaries reject another revision even if its generation matches.  Every
bundle fact must carry the snapshot generation.  The existing V1 closure and
materialization receipt formats remain unchanged.  This binding assumes the
caller supplies a source-owned revision; independently authenticating a remote
provider revision remains an upstream source-admission obligation.
After atomic materialization, the in-process =MaterializedClosure= retains the
checked bundle identity and snapshot digest and can reject reuse against a
different bundle, generation, or same-generation source revision.  Its inner
V1 =DerivationReceipt= digest alone does not certify the source snapshot.
Persistent transport of this binding needs a separately governed format.
The read-only physical comparison also accepts complete candidate rows with
caller-projected =RuleId= and ordered source =FactId= support.  It checks the
exact pair set, shortest distance, rule, and support against the bound Ascent
evaluation.  This comparison is evidence of parity for supplied rows, not a
source-owner attestation or a lineage admission.
That value includes an identity-complete =DerivationReceipt= with =RulePackId=,
input generation and facts, caller-assigned derived =FactId=s and =DerivationId=s,
complete closure status, and a digest bound to the pre-admission closure digest.

The admission contract is all-or-nothing.  Let (C) be the ordered candidate
receipt, (I) the ordered identity assignment, and (g_t) the requested target
generation.  Admission is defined only for a complete receipt with a bijective
identity binding, unique identities, and candidates evaluated at (g_t).

#+begin_src typst
#set page(width: 15cm, height: auto, margin: 1.2cm)
#let complete(C) = $ "status"(C) = "Complete" $
#let unique(xs) = $ forall i, j: i != j => xs_i != xs_j $
#let bound(C, I, g_t) = $
  complete(C) and |C| = |I|
  and unique("fact"(I)) and unique("derivation"(I))
  and forall c in C: "generation"(c) = g_t
$
#let materializable(C, I, g_f, g_t) = $
  bound(C, I, g_t)
  and "LineageAccepted"(C, I)
  and "TransitionAccepted"(g_f, g_t)
$

$
  "admit"(C, I, g_f, g_t) =
  cases(
    (
      "Transition"(g_f, g_t, "Lineage"(C, I)),
      &"if" materializable(C, I, g_f, g_t),
    ),
    ("Error", &"otherwise"),
  )
$

No prefix of $C$ is observable: lineage rejection or transition rejection
produces no `MaterializedClosure`.
#+end_src

The executable contract rejects truncated receipts, candidate/identity count
mismatches, duplicate fact or derivation identities, cross-generation candidates,
self-support rejected by =mrr-lineage=, and invalid generation transitions rejected
by =mrr-transition=.  Candidate sorting remains owned by =mrr-ascent=; identity
allocation and live publication remain outside this pure admission function.

=BundleAdmission.lean= kernel-checks this boundary with
=admitted_closure_binding_is_exact= and
=closure_admission_rejects_any_failed_owner=.  The uv-managed impact owner maps
changes in =meta-relational-reasoning=, or in its transitive MRR dependencies,
to those obligations before pinned local Lean admission.
* Executable Org-Babel validation

The uv-managed =MRRProof= project owns executable validation of architecture
Babel blocks through =mrr_proof_validation.org_babel=. Its CLI remains a thin
receipt and local Lean orchestration layer. The validator extracts exact Org source
provenance, rejects =:file= outputs and unclosed blocks, and emits block counts
inside the proof-impact receipt.

Mermaid =flowchart=/=graph= blocks are checked by the native flowchart grammar
shipped with the workspace =mermaid-cli= package.  A no-op AST sink exercises
the grammar without DOM, Puppeteer, Chrome, rendering, SVG, or repository
outputs.  Unsupported diagram families fail closed until their native grammar
is explicitly admitted.  Every Typst block is compiled independently and
concurrently from stdin to stdout with system-font discovery disabled; embedded Typst fonts remain
available and the PDF bytes are discarded.  Consequently this validation is
part of the same local-impact and local Lean commands as the proof, with
=outputs=none=.
