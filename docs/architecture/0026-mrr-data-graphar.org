* Purpose

This RFC records only the upstream MRR side of the =mrr-data=
boundary.  The canonical data-plane design is owned by the separate
[[https://github.com/tao3k/mrr-data/blob/main/docs/architecture/0001-mrr-data-plane.org][mrr-data RFC 0001]].
It specifies Arrow mapping, GraphAr projection, CID/CAR packaging, security,
repository shape, and delivery milestones.  Those details are not duplicated
here because that would create two drifting specifications.

The boundary is implemented for lossless Arrow relation batches, local
Manifest V1 and CID/CAR validation, and a maintained native GraphAr
write/read projection slice.  The GraphAr reader now reconstructs physical
endpoints through persisted =EntityId= properties, restores every MRR identity
and =RelationContext= field, and re-admits the complete fact through its owning
relation.  Same-fixture differential and performance Scenarios cover the
maintained native path.  Physical query binding, the identity-safe
result-candidate bridge, and the first engine-specific schema-bound slice are
implemented downstream.  That slice executes one admitted single-hop
binary-Entity query through the same DataFusion plan after Arrow round-trip and
GraphAr native read, then proves identical candidate and admission receipts.
Broader query shapes, cross-engine result parity, and distributed providers
remain open.  This RFC therefore records a partially implemented boundary
rather than claiming a complete data plane.

* Ownership and dependency direction

MRR owns:

- =EntityId=, =RelationId=, =FactId=, =GenerationId=, and =RevisionId=;
- =RelationSchema=, =Fact=, =RelationContext=, and canonical value semantics;
- =ExternalRevisionIdentity=, =RevisionBinding=, and =SemanticSnapshot=;
- =RelationCatalogDigest=, =EntityCatalogDigest=, and storage-neutral
  =CatalogBoundQuery= admission;
- =MetaQueryIr=, lineage, transitions, receipts, and semantic admission.

The downstream =mrr-data= repository may consume those contracts and own:

- deterministic Arrow physical interchange;
- a gated GraphAr Property Graph projection;
- physical snapshot manifests, block CIDs, and CAR archives;
- filesystem, object-store, or later distribution providers;
- a bound query wrapper that identifies an exact catalog and snapshot;
- an engine-profile-checked output bridge from identity-free physical rows to an
  MRR-owned result candidate.

The dependency direction is one way:

MRR must never acquire a reverse dependency on =mrr-data=, Arrow, GraphAr,
IPLD, CAR, IPFS, or a database engine.

* Calibrations imposed by current MRR contracts

The current relation model is typed and n-ary.  A fact contains a
=RelationId=, an ordered vector of =Value= instances, and a =RelationContext=
carrying generation, authority, provenance, completeness, and validity.
Consequently:

1. Arrow batches must be relation-specific and lossless.  A universal
   subject/predicate/object table is at most an optional view for binary
   relations, not MRR's canonical relation form.
2. GraphAr is a specialization for the graph-shaped subset.  Binary
   Entity-to-Entity relations can become edges; unsupported n-ary or mixed
   value relations must be reified by a versioned profile or rejected.
3. GraphAr internal vertex IDs, row positions, chunks, and adjacency offsets
   are physical identifiers and cannot replace MRR IDs.
4. CID identifies exact encoded bytes.  It is not =GenerationId=, semantic
   equality, authority, or admission.
5. Source revisions use MRR's provider-neutral =RevisionBinding= and an
   admitted =SemanticSnapshot= binds the complete source set to one generation.  Jujutsu
   ChangeId/CommitId values are one possible provider payload, not fields that
   MRR hard-codes for all sources.

MRR's =ValueSchema= now expresses decimal precision and scale, float width,
temporal units and timezone policy, recursive list element shape, ordered
record shape, and nullability.  Generic key, uniqueness, and functional
dependency constraints no longer encode graph cardinality into the core.
A downstream Arrow adapter must map this structure losslessly or reject the
schema with a typed error; it still may not infer physical Arrow or GraphAr
semantics from a coarse runtime value tag.

* Query binding boundary

=MetaQueryIr= remains storage-neutral but not model-free: its node, relation,
property, direction, path, filter, and result operators describe a Property
Graph query model.  It intentionally does not carry Arrow schemas, GraphAr
manifests, engine plans, or physical IDs.

MRR now admits a =CatalogBoundQuery= that pairs =MetaQueryIr= with:

- the exact =GenerationId= from an admitted =SemanticSnapshot=;
- the exact =RelationCatalogDigest= and =EntityCatalogDigest=;
- the semantic snapshot digest;
- a digest of the canonical query and the complete binding.

This admission resolves explicit entity and relation references, statically
checks expressions, parameters, aggregations, grouping, and output rows through
RFC 0031, and rejects bundle facts from another generation.  Query templates
with dependencies still fail closed until their plan graph has a canonical
admission contract.

The downstream =BoundDataQuery= now extends that binding with:

- a physical snapshot root CID;
- an optional GraphAr projection profile and manifest CID;
- an engine capability profile.

The generation must resolve to an admitted upstream =SemanticSnapshot=.
Physical snapshot roots remain downstream identities and cannot replace its
source-revision digest.

The downstream binder validates physical availability, projection profile,
snapshot root, and engine capability.  Engines retain their native synchronous
or asynchronous lifecycle; the physical-output bridge rejects rows produced
under a profile outside the exact binding, accepts only identity-free columns
and rows, and injects =QueryResultBinding= from =CatalogBoundQuery=.  It
consumes MRR's admitted catalog binding rather than reimplementing
unknown-label, unknown-property, relation-type, expression-type, engine
lifecycle, or result-admission semantics under a second error vocabulary.

For catalog $S_g$, snapshot $D_g$, and query $q$, execution is defined only
when every query reference resolves uniquely and all identities name the same
generation.

Parsing, schema binding, execution, and semantic admission therefore produce
different receipts.  Parser acceptance cannot establish that a property
exists, that a snapshot is current, or that a result is authoritative.

* Content and Context materialization

The same physical store may contain canonical Content and derived Context, but
their identities and receipts remain different:

- Content is durable, source-bound, versioned, and admitted;
- Context is a task/actor/capability-scoped projection bound to an exact
  Content generation, projection policy, selection lineage, and expiry;
- storage import, graph merge, CID availability, or query success cannot
  promote Context into Content.

This separation is semantic and survives changes of Arrow batch, GraphAr
layout, database engine, object store, or transport.

* Upstream obligations before implementation

MRR should change only when a concrete downstream proof exposes a missing
semantic contract.  The first expected decisions are:

1. prove the complete =ValueSchema= to Arrow mapping, including canonical
   decimal, temporal, nested nullability, and record-field ordering;
2. the canonical byte representation for MRR IDs at foreign-data boundaries;
3. prove how RFC 0031 query types map to physical engine and Arrow types without
   weakening their nullability or numeric constraints;
4. which receipt fields MRR must admit after a physical round trip.

MRR V1 preserves duration values as canonical source lexical text.  Until a
separate semantic duration contract specifies month/day/nanosecond components,
the lossless Arrow representation is UTF-8 plus namespaced MRR extension
metadata.  A downstream adapter must not guess units from the spelling or
silently coerce it into Arrow's fixed-unit duration type.

No Arrow or GraphAr dependency is justified merely to answer those questions.

* Next execution sequence

The active implementation line returns to the MRR repository after the native
GraphAr read path is fixed by executable downstream performance evidence.  The
next work is the semantic-to-physical query boundary, not another storage
optimization or a reverse Arrow/GraphAr dependency in MRR.

The dependency order is:

1. MRR specifies and admits a candidate query-execution receipt bound to the
   existing =CatalogBoundQuery= digest, generation, relation and entity catalog
   digests, semantic snapshot digest, and ordered static result schema.  A
   stale generation, catalog mismatch, missing field, reordered field,
   incompatible value, or nullability violation publishes no admitted result.
   This step is implemented by RFC 0032.
2. =mrr-data= implements =BoundDataQuery= as a downstream physical binding.
   It adds the physical snapshot root, optional GraphAr projection profile,
   and engine capability evidence, but consumes MRR's admitted catalog and
   typing receipt instead of implementing a second resolver or type checker.
   Its result bridge verifies the producer profile and injects MRR identity
   rather than accepting an engine-authored binding or owning a second engine
   runtime.  This step is implemented downstream.
3. Cross-repository Scenarios execute the same admitted query through the
   Arrow and maintained GraphAr paths using one DataFusion plan, compare
   ordered typed results, and
   exercise stale-generation, catalog-drift, projection-mismatch, and
   unsupported-capability failures.  The corpus and sample count may not be
   reduced to make a performance gate pass.  The first exact query slice is
   implemented downstream; widening it requires new typed negative contracts.
4. Only after that result-admission chain is executable should the frontend
   widen the bounded GQL/Cypher surface.  Optional matching, quantified paths,
   and query composition require explicit =MetaQueryIr= ownership and static
   typing.  Catalog management, mutation, procedures, and session control stay
   fail-closed while MRR has no public semantic model for them.
5. POO Flow and Agent consumers receive only MRR-admitted Content or
   generation-bound Context projections.  A successful database query remains
   candidate evidence and cannot bypass lineage, completeness, and transition
   admission.

The first MRR deliverable, the query-result admission contract and its Rust,
negative-contract, canonical-identity, and Lean evidence, is implemented by
RFC 0032.  The physical binder and result-candidate bridge that consume that
contract and the first engine-specific differential Scenario are also
implemented downstream.  The active deliverable is now typed widening of the
engine slice and measured execution performance, not another binding or
runtime layer.  Remote distribution, IPFS, and broader provider work remain
deferred because they do not block this chain.

* Cross-repository acceptance gates

The boundary becomes complete only when the downstream repository provides,
in dependency order:

1. property-tested =Fact -> Arrow -> Fact= round trips preserving every MRR
   identity and context field;
2. typed rejection for ambiguous or unsupported value schemas;
3. a deterministic Manifest V1 and root-CID over the proven Arrow encoding;
4. CAR import validation and resource-limit scenarios;
5. a GraphAr projection that preserves MRR identities through repartition and
   rejects unowned n-ary mappings;
6. stale-generation, catalog-drift, missing-projection, and
   unsupported-capability query-binding tests;
7. differential GraphAr reader evidence and performance scenarios without
   reducing the declared corpus;
8. proof that MRR has no reverse storage dependency;
9. a physical-output bridge proving that a physical engine cannot author MRR
   result identity and that profile drift publishes no candidate;
10. same-query ordered typed-result parity through the selected Arrow and
    maintained GraphAr engine paths.

Gates 1--10 have implementation evidence for the declared single-hop
binary-Entity DataFusion slice.  Gate 7 is runner-specific A/B evidence and a
regression guard, not a universal throughput claim; gate 10 is not evidence of
broader query-shape or cross-engine parity.  The authoritative downstream
implementation status lives in =mrr-data= RFC 0001; this RFC owns only the MRR
obligations and dependency direction.
