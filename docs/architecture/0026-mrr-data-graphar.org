* Purpose

This RFC records only the upstream MRR side of the proposed =mrr-data=
boundary.  The canonical data-plane design is owned by the separate
[[https://github.com/tao3k/mrr-data/blob/main/docs/architecture/0001-mrr-data-plane.org][mrr-data RFC 0001]].
It specifies Arrow mapping, GraphAr projection, CID/CAR packaging, security,
repository shape, and delivery milestones.  Those details are not duplicated
here because that would create two drifting specifications.

Both RFCs remain proposals.  The =mrr-data= repository does not yet implement
the data plane, and this repository does not claim Arrow, GraphAr, CID, CAR, or
schema-bound execution support.

* Ownership and dependency direction

MRR owns:

- =EntityId=, =RelationId=, =FactId=, =GenerationId=, and =RevisionId=;
- =RelationSchema=, =Fact=, =RelationContext=, and canonical value semantics;
- =ExternalRevisionIdentity=, =RevisionBinding=, and =SemanticSnapshot=;
- =RelationCatalogDigest= and storage-neutral =CatalogBoundQuery= admission;
- =MetaQueryIr=, lineage, transitions, receipts, and semantic admission.

The downstream =mrr-data= repository may consume those contracts and own:

- deterministic Arrow physical interchange;
- a gated GraphAr Property Graph projection;
- physical snapshot manifests, block CIDs, and CAR archives;
- filesystem, object-store, or later distribution providers;
- a bound query wrapper that identifies an exact catalog and snapshot.

The dependency direction is one way:

MRR must never acquire a reverse dependency on =mrr-data=, Arrow, GraphAr,
IPLD, CAR, IPFS, or a database engine.

* Calibrations imposed by current MRR contracts

The current relation model is typed and n-ary.  A fact contains a
=RelationId=, an ordered vector of =Value= instances, and a =RelationContext=
carrying generation, authority, provenance, completeness, and validity.
Consequently:

1. Arrow batches must be relation-specific and lossless.  A universal
   subject/predicate/object table is at most an optional view for binary
   relations, not MRR's canonical relation form.
2. GraphAr is a specialization for the graph-shaped subset.  Binary
   Entity-to-Entity relations can become edges; unsupported n-ary or mixed
   value relations must be reified by a versioned profile or rejected.
3. GraphAr internal vertex IDs, row positions, chunks, and adjacency offsets
   are physical identifiers and cannot replace MRR IDs.
4. CID identifies exact encoded bytes.  It is not =GenerationId=, semantic
   equality, authority, or admission.
5. Source revisions use MRR's provider-neutral =RevisionBinding= and an
   admitted =SemanticSnapshot= binds the complete source set to one generation.  Jujutsu
   ChangeId/CommitId values are one possible provider payload, not fields that
   MRR hard-codes for all sources.

MRR's =ValueSchema= now expresses decimal precision and scale, float width,
temporal units and timezone policy, recursive list element shape, ordered
record shape, and nullability.  Generic key, uniqueness, and functional
dependency constraints no longer encode graph cardinality into the core.
A downstream Arrow adapter must map this structure losslessly or reject the
schema with a typed error; it still may not infer physical Arrow or GraphAr
semantics from a coarse runtime value tag.

* Query binding boundary

=MetaQueryIr= remains storage-neutral but not model-free: its node, relation,
property, direction, path, filter, and result operators describe a Property
Graph query model.  It intentionally does not carry Arrow schemas, GraphAr
manifests, engine plans, or physical IDs.

MRR now admits a =CatalogBoundQuery= that pairs =MetaQueryIr= with:

- the exact =GenerationId= from an admitted =SemanticSnapshot=;
- a canonical digest of the ordered =RelationSchema= catalog;
- the semantic snapshot digest;
- a digest of the canonical query and the complete binding.

This admission resolves explicit relation references and rejects bundle facts
from another generation.  It deliberately does not claim property-level type
checking: MRR does not yet own an entity/property catalog.  Query templates
with dependencies also fail closed until their plan graph has a canonical
admission contract.

A future downstream =BoundDataQuery= may extend that binding with:

- a physical snapshot root CID;
- an optional GraphAr projection profile and manifest CID;
- language/dialect and engine capability declarations.

The generation must resolve to an admitted upstream =SemanticSnapshot=.
Physical snapshot roots remain downstream identities and cannot replace its
source-revision digest.

For catalog $S_g$, snapshot $D_g$, and query $q$, execution is defined only
when every query reference resolves uniquely and all identities name the same
generation.

$
  "well-typed"(q, S_g)

$
  "executable"(q, D_g)
  := "well-typed"(q, S_g)
  and "catalog-digest"(q) = "digest"(S_g)
  and "generation"(q) = "generation"(D_g) = g
$

A database result is a candidate. It becomes Content only after MRR source,
lineage, completeness, and transition owners admit it at the same generation.
#+end_src

Parsing, schema binding, execution, and semantic admission therefore produce
different receipts.  Parser acceptance cannot establish that a property
exists, that a snapshot is current, or that a result is authoritative.

* Content and Context materialization

The same physical store may contain canonical Content and derived Context, but
their identities and receipts remain different:

- Content is durable, source-bound, versioned, and admitted;
- Context is a task/actor/capability-scoped projection bound to an exact
  Content generation, projection policy, selection lineage, and expiry;
- storage import, graph merge, CID availability, or query success cannot
  promote Context into Content.

This separation is semantic and survives changes of Arrow batch, GraphAr
layout, database engine, object store, or transport.

* Upstream obligations before implementation

MRR should change only when a concrete downstream proof exposes a missing
semantic contract.  The first expected decisions are:

1. prove the complete =ValueSchema= to Arrow mapping, including canonical
   decimal, temporal, nested nullability, and record-field ordering;
2. the canonical byte representation for MRR IDs at foreign-data boundaries;
3. define the missing entity/property catalog before claiming property-level
   query type checking;
4. which receipt fields MRR must admit after a physical round trip.

No Arrow or GraphAr dependency is justified merely to answer those questions.

* Cross-repository acceptance gates

The proposal becomes implemented only when the downstream repository provides:

1. deterministic Manifest V1 and root-CID tests;
2. property-tested =Fact -> Arrow -> Fact= round trips preserving every MRR
   identity and context field;
3. typed rejection for ambiguous or unsupported value schemas;
4. CAR import validation and resource-limit scenarios;
5. a GraphAr projection that preserves MRR identities through repartition and
   rejects unowned n-ary mappings;
6. stale-generation, catalog-drift, dialect-mismatch, and unknown-property
   query-binding tests;
7. differential GraphAr reader evidence and performance scenarios without
   reducing the declared corpus;
8. proof that MRR has no reverse storage dependency.

Until those gates pass, this RFC defines a boundary only.  The authoritative
implementation plan and its current status live in =mrr-data= RFC 0001.
