* Bootstrap and stale ABI recovery

The existing acquisition glue reads the single declared revision. It delegates
Core, dependency installation and product build to the selected source owner's
maintained Just entrypoints. Its old Python =prepare_native_pins= import is no
longer an upstream API and is removed. Python does not select compiler flags,
reimplement package resolution or own the build algorithm. Gerbil's package APIs
and the producer's =build.ss= retain those responsibilities.

The initial retained-prefix migration fails with an object initializer arity
error after the POO revision changes. A checkout identity alone does not qualify
previously compiled dynamic modules. The failed prefix is preserved. The same
revision is rebuilt into an independent empty library prefix, leaving the old
source and evidence intact. =gxpkg uninstall= is never used. Installed outputs
must come from one admitted source/ABI cohort before the full MRR entry can pass.

This bootstrap is separate from the new upstream embedded build/test capability.
MRR's frozen Gerbil bridge cannot be described as consuming that newer API. Its
CLI bootstrap remains explicit until a separately authorized bridge adoption.

MRR's =build.ss= now uses standard Gerbil =defbuild-script= targets and
=pkg-config-cflags= / =pkg-config-libs= for its declared OpenSSL dependency.
The former ASP building helper was an undeclared dependency exposed by the
migration; it is removed rather than installed as another production owner.
The package still publishes its complete link-input receipt atomically. Neither
Python nor CI injects additional compiler or linker policy.
