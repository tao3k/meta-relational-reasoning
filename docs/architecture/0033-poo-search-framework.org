#+title: POO Search Framework Ownership
#+startup: overview

* Decision

POO Flow =modules/search= owns backend-neutral POO stage roles, typed
composition, strategies, and DAG declarations.  MRR owns only the
=generation= and factor-identity projection in
=scheme/search/projection.ss=, plus native Ascent, lineage, and semantic
admission.  ASP owns its Playbook syntax, concrete operators, resident
execution, scoring policy, and public result projection.

The source dependency direction is POO Flow -> MRR -> ASP.  A POO Flow
strategy is inert until a consumer executes it.  MRR projects its factor
identities and binds observations to one consumer-supplied generation; this
projection is reasoning input, not proof of runtime execution.

MRR does not reconstruct the Playbook or publish a second operator registry.
The strategy, factor projection, and native generation must be bound to the
same admitted source identity before downstream use.

* Module and package boundary

POO Flow Core supplies the POO object model, Flow composition, and graph/DAG
receipts.  POO Flow =modules/query= supplies a common Scheme Query declaration,
admission, selection, and Provider-binding entry point.  Its
=modules/temporal-causality= supplies inert structural Impact, causal event
graphs, temporal classification, and trajectory assessment.  Its
=modules/reverse-inference= is a separate, bounded candidate engine: it uses
GQL selection and Scheme Ascent to compare source-labelled hypotheses, but
does not authenticate sources or authorize actions.

MRR Scheme packages MRR-specific grammar projections, ReasoningBundle
declarations, bounded resource sequencing, and a Search factor projection.  It
specializes POO Flow contracts without copying Core, Query, causal algorithms,
or the ASP Playbook.  MRR native crates own typed relations/rules, bounded
Ascent candidate evaluation, identity, lineage, Impact, and fail-closed semantic
admission.  A =lambda-*= library supplies domain Query/Case modules; Cargo
features may select optional domain and physical libraries at build time.
An application backend such as Marlin performs runtime work and returns
candidates.  Package dependency is one-way: MRR's =gerbil.pkg= directly pins
POO Flow; POO Flow owns the transitive parser edge and tracks Core as a
subtree.

The public bridge must carry exact source/query identity, semantic generation,
bounded result contract, provenance, and execution candidate/receipt.  The
Scheme declaration is inert until the owning backend executes it; MRR then
checks semantic admission.  Neither a compile-time feature nor an Ascent or
causal candidate grants runtime authority.

* POO object model

The framework has four orthogonal stage roles:

| Role | Abstract responsibility | Concrete owner |
|-
| acquisition | produce a candidate frontier | ASP or another consumer |
| refinement | transform or rank an existing frontier | ASP or another consumer |
| reasoning | derive graph or relational evidence from a typed frontier | MRR-capable consumer |
| projection | form a bounded public result from admitted evidence | ASP or another consumer |

A stage binds a stable name, an opaque consumer operation, arguments, an input
domain, and an output domain.  A concrete consumer role can inherit one of the
abstract roles and add backend-specific slots.  The POO Flow framework never
switches on those backend slots.

Each stage is also a Search factor.  A consumer runtime emits immutable factor
observations with a candidate identity, logical position, provenance identity,
and causal parents.  MRR delegates causal event-graph construction, trajectory
assessment, temporal cuts, and structural Impact to POO Flow's existing
=temporal-causality= module; it does not duplicate those algorithms.
For competing explanations, a consumer may separately call POO Flow's
=reverse-inference= Case with source-labelled claims and explicit opposing
branches.  Its =supported= status is hypothetical fit, not a semantic admission
receipt or evidence authentication.  MRR may attach its output as a candidate
with lineage only after the relevant source and generation checks.

A composition is either sequential, parallel, or an explicit merge of a
parallel composition.  Sequential edges are admitted only when the preceding
output domain equals the following input domain.  Parallel branches must share
one input domain.  A merge is an ordinary typed stage; therefore conjunction,
ranking joins, union, or any other aggregation semantics remain explicit and
consumer-owned.

A POO Flow strategy binds one root composition and policy metadata.  It is
declarative: the execution owner remains the consumer runtime.  MRR projects
the strategy with a nonempty consumer-supplied generation canonical input.
The projection requires distinct stable ASCII stage names (lowercase letters,
digits, and hyphens) and emits rows of =(factor canonical input, role name)=
and directed edges between factor canonical inputs.  Sequential and explicit merge composition produce edges;
parallel branches do not acquire edges merely by sharing an input.

The factor canonical input is the UTF-8 byte sequence
=mrr.search.factor.v1:<strategy-name>:<stage-name>=.  A Rust consumer derives
each =QueryOperatorId= from those exact bytes with
=SearchFactor::from_canonical_input=, maps the projected role name to its
=SearchFactorRole=, and derives the =GenerationId= from the strategy's
projection's generation canonical input with
=GenerationId::from_canonical_bytes=.  It
resolves projected edge endpoints through the resulting factor IDs.  The
generation input is supplied by the execution owner; MRR does not invent a
runtime generation.  The MRR Scheme observation constructor requires both a
member stage of the POO Flow strategy and the same generation input.  Native
=SearchObservation= stores a typed generation and =evaluate_search_factors=
rejects any observation from another generation before Ascent inference.
The cross-language projection remains an explicit consumer binding contract;
there is no live Scheme-to-Rust adapter in ASP yet.

* Ascent and lineage integration

=mrr-search= is the native, backend-neutral reasoning adapter.  Downstream
systems register factor identities and roles, directed factor edges, and
generation-bound observations.  The adapter first rejects generation mismatch,
duplicate or unknown
factors, cyclic factor graphs, missing causal parents, temporal inversions,
causal-parent edges that disagree with the factor graph, and budget overflow.

Only after admission does a small Ascent program derive the transitive factor
influence relation for each observed candidate.  A deterministic breadth-first
reconstruction must reproduce Ascent's shortest distance; disagreement is an
internal error, not a partial result.  The resulting factor trajectory is
projected into =mrr-lineage=.  Therefore a changed observation can use the
existing =IMPACT= operation to classify direct and transitive invalidation.

Ascent does not rank source text, parse regexes, tokenize documents, choose a
backend, or assign relevance scores.  Those are factor-owned observations or
consumer policy.  Keeping the Ascent relation set to factor reachability and
candidate influence prevents Core and Search from repeating a broad retrieval.

* Why the removed Playbook was wrong

The former =scheme/search/playbook.ss= combined three authorities:

1. ASP command-language parsing and concrete operator registration;
2. POO Flow composition;
3. MRR package identity.

That made MRR a second source of truth for ASP syntax and allowed its operator
set to drift independently.  Renaming or extending an ASP leaf then required a
new MRR release even though no meta-relational semantic contract had changed.
The module and its package test are removed rather than retained as a
compatibility surface.

* Mathematical contract

Let a stage be a typed arrow =f : A -> B=.  The framework admits sequential
composition only for =f : A -> B= and =g : B -> C=, producing
=g o f : A -> C=.  Parallel composition admits arrows
=f_i : A -> B_i= sharing one domain and produces
=<f_1, ..., f_n> : A -> (B_1 * ... * B_n)=.  An aggregation is not inferred:
it is another consumer-supplied arrow from that product domain.

This is structural safety, not a relevance theorem.  Precision, recall,
coverage, generation completeness, and graph-admission proofs remain separate
receipts owned by the concrete search and reasoning layers.

#+begin_src typst
#set page(width: 150mm, height: auto, margin: 14mm)
#set text(size: 10pt)

= POO Search composition

For typed arrows $f: A arrow B$ and $g: B arrow C$, sequential composition is
$g compose f: A arrow C$. Parallel composition is admitted only for a shared
domain: $f: A arrow B$ and $g: A arrow C$ produce
$"parallel"(f, g): A arrow (B times C)$. Aggregation is a separate arrow
$m: (B times C) arrow D$; the framework never invents $m$.
#+end_src

The executable counterpart is
=proofs/MRRProof/BundleAdmission.lean=.  Its admissions carry the boundary
equalities as proof fields, so a successful receipt cannot represent a
mismatched sequential, parallel, or merge edge.

* Migration gate

The former =scheme/search/core.ss= and its duplicate typed-composition test
are removed.  POO Flow Search PR #33 owns the composition implementation and
its focused executable test.  MRR's =scheme/search/projection.ss= retains the
MRR-specific canonical factor identity, generation binding, and edge relation;
its test consumes POO Flow objects directly.  MRR pins the exact POO Flow
revision containing =modules/search= before its package build can use this
migration.

The Rust =mrr-search= adapter still accepts caller-supplied factor identities
and observations.  No live ASP Scheme-to-Rust bridge currently proves they
were projected from the same POO Flow declaration.  The DAG receipt remains
plan evidence, not an execution receipt.

* Acceptance

- MRR exports no =compile-search-playbook= or =defsearch-playbook= API.
- The framework source contains no concrete search engine name.
- C3-composed consumer roles remain visible on stage objects.
- factor observations reuse the POO Flow temporal-causality objects;
- Ascent derives only bounded factor influence and emits deterministic paths;
- every published influence has reusable MRR lineage and Impact;
- mismatched sequential domains and parallel branch domains fail closed;
- a merge cannot run unless its input equals the parallel product domain;
- factor identity inputs and edges are stable, and cross-generation
  observations fail before native factor inference;
- generated DAG receipts remain declarations and do not claim runtime work.
