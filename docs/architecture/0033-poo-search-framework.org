#+title: POO Search Framework Ownership
#+startup: overview

* Decision

POO Flow owns the backend-neutral Search object and composition framework.
MRR consumes that framework for GQL, bounded Ascent factor influence, lineage,
and semantic Impact.  ASP owns its Search Playbook, concrete search operators,
resident execution, scoring policy, and public projection.

The source dependency direction is POO Flow -> MRR -> ASP.  At runtime ASP
provides admitted candidate and relation facts to MRR's semantic stages and
receives bounded derivation receipts.  POO Flow's DAG receipt describes a plan;
it is not evidence that ASP executed it.

MRR does not reconstruct the Playbook from strings or publish a second operator
registry.  ASP does not replace the POO Flow Search object model with a private
semantic plan.  A consumer may keep a wire projection, but it must be derived
from the admitted POO declaration and checked against its identity.

* POO object model

The framework has four orthogonal stage roles:

| Role | Abstract responsibility | Concrete owner |
|-
| acquisition | produce a candidate frontier | ASP or another consumer |
| refinement | transform or rank an existing frontier | ASP or another consumer |
| reasoning | derive graph or relational evidence from a typed frontier | MRR-capable consumer |
| projection | form a bounded public result from admitted evidence | ASP or another consumer |

A stage binds a stable name, an opaque consumer operation, arguments, an input
domain, and an output domain.  A concrete consumer role can inherit one of the
abstract roles and add backend-specific slots.  The POO Flow framework never
switches on those backend slots.

Each stage is also a Search factor.  A consumer runtime emits immutable factor
observations with a candidate identity, logical position, provenance identity,
and causal parents.  POO Flow owns event-graph construction, trajectory
assessment, temporal cuts, and structural Impact in its existing
=temporal-causality= module.  MRR consumes those admitted observations.

A composition is either sequential, parallel, or an explicit merge of a
parallel composition.  Sequential edges are admitted only when the preceding
output domain equals the following input domain.  Parallel branches must share
one input domain.  A merge is an ordinary typed stage; therefore conjunction,
ranking joins, union, or any other aggregation semantics remain explicit and
consumer-owned.

A strategy binds one root composition to policy metadata.  It is declarative:
the execution owner remains the consumer runtime.

* Ascent and lineage integration

=mrr-search= is the native, backend-neutral reasoning adapter.  Downstream
systems register factor identities and roles, directed factor edges, and
generation-bound observations.  The adapter first rejects duplicate or unknown
factors, cyclic factor graphs, missing causal parents, temporal inversions,
causal-parent edges that disagree with the factor graph, and budget overflow.

Only after admission does a small Ascent program derive the transitive factor
influence relation for each observed candidate.  A deterministic breadth-first
reconstruction must reproduce Ascent's shortest distance; disagreement is an
internal error, not a partial result.  The resulting factor trajectory is
projected into =mrr-lineage=.  Therefore a changed observation can use the
existing =IMPACT= operation to classify direct and transitive invalidation.

Ascent does not rank source text, parse regexes, tokenize documents, choose a
backend, or assign relevance scores.  Those are factor-owned observations or
consumer policy.  Keeping the Ascent relation set to factor reachability and
candidate influence prevents Core and Search from repeating a broad retrieval.

* Why the removed Playbook was wrong

The former =scheme/search/playbook.ss= combined three authorities:

1. ASP command-language parsing and concrete operator registration;
2. POO Flow composition;
3. MRR package identity.

That made MRR a second source of truth for ASP syntax and allowed its operator
set to drift independently.  Renaming or extending an ASP leaf then required a
new MRR release even though no meta-relational semantic contract had changed.
The module and its package test are removed rather than retained as a
compatibility surface.

* Mathematical contract

Let a stage be a typed arrow =f : A -> B=.  The framework admits sequential
composition only for =f : A -> B= and =g : B -> C=, producing
=g o f : A -> C=.  Parallel composition admits arrows
=f_i : A -> B_i= sharing one domain and produces
=<f_1, ..., f_n> : A -> (B_1 * ... * B_n)=.  An aggregation is not inferred:
it is another consumer-supplied arrow from that product domain.

This is structural safety, not a relevance theorem.  Precision, recall,
coverage, generation completeness, and graph-admission proofs remain separate
receipts owned by the concrete search and reasoning layers.

= POO Search composition

For typed arrows $f: A arrow B$ and $g: B arrow C$, sequential composition is
$g compose f: A arrow C$. Parallel composition is admitted only for a shared
domain: $f: A arrow B$ and $g: A arrow C$ produce
$"parallel"(f, g): A arrow (B times C)$. Aggregation is a separate arrow
$m: (B times C) arrow D$; the framework never invents $m$.
#+end_src

The executable counterpart is
=proofs/MRRProof/BundleAdmission.lean=.  Its admissions carry the boundary
equalities as proof fields, so a successful receipt cannot represent a
mismatched sequential, parallel, or merge edge.

* Migration gate

The POO Flow Search module is the source authority for stage roles and typed
composition.  MRR removes its former =scheme/search/core.ss= implementation
rather than retaining a forwarding compatibility module.  The MRR Rust
=mrr-search= adapter still accepts caller-supplied factor identities and
observations; it does not yet verify that they were projected from the same
POO Flow Search strategy.  Its receipt is reasoning evidence, not runtime
execution evidence.

The first cross-language gate must bind one POO Flow strategy and DAG receipt to
MRR factor identities, a generation-bound observation set, one parser-owned GQL
=MetaQueryIr=, and one bounded Ascent result.  ASP may adopt the new POO Flow
revision only after that exact interface is published and its existing Playbook
parser lowers into the admitted POO declaration.  Until then, the diagram above
is the target composition rather than an end-to-end conformance claim.

* Acceptance

- MRR exports no =compile-search-playbook= or =defsearch-playbook= API.
- The framework source contains no concrete search engine name.
- C3-composed consumer roles remain visible on stage objects.
- factor observations reuse the POO Flow temporal-causality objects;
- Ascent derives only bounded factor influence and emits deterministic paths;
- every published influence has reusable MRR lineage and Impact;
- mismatched sequential domains and parallel branch domains fail closed;
- a merge cannot run unless its input equals the parallel product domain;
- generated DAG receipts remain declarations and do not claim runtime work.
