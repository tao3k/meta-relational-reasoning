* Bounded semantic slice

#+begin_src mermaid
flowchart LR
  B[Validated ReasoningBundle] --> C[Selected RulePack]
  C --> A[Bounded Ascent closure]
  A --> W[Deterministic shortest witness]
  W --> R[ClosureReceipt]
  R --> F[Facade identity and lineage admission]
#+end_src

The adapter accepts one validated binary source relation, one binary derived
relation, and exactly two rules from one named rule pack.  Input count and the
finite node-pair upper bound are checked before Ascent runs.  Output truncation
is explicit and cannot be admitted as a complete generation delta.

* Receipt and authority

The pre-admission =ClosureReceipt= binds the selected =RulePackId=, input
=GenerationId=, sorted complete input =FactId= set, closure status, sorted
derivation candidates, and a domain-framed SHA-256 digest.  Repeating the same
evaluation therefore yields the same receipt digest.

#+begin_src typst
#let closure-receipt(pack, generation, inputs, status, candidates) = (
  pack: pack,
  generation: generation,
  inputs: inputs.sorted(),
  status: status,
  candidates: candidates.sorted(),
)
$ digest = sha256("mrr.derivation-receipt.v1" || encode(closure-receipt)) $
#+end_src

Ascent does not allocate =FactId= or =DerivationId=.  Caller-assigned identities
remain external and become authoritative only after the facade composes the
canonical lineage and transition validators.  This is the corrected MRR
architecture, not a compatibility path: execution, identity, lineage, and
transition each have exactly one owner.

* Verification

- transitive dependency derives the expected indirect pair;
- cyclic input reaches a finite fixed point with shortest support;
- repeated evaluation is byte-for-byte receipt-idempotent;
- a rule outside the selected rule pack fails closed;
- input, theoretical pair, and result budgets remain explicit.
